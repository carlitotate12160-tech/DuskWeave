# Start DuskWeave

## Setup scope

Use this guide for workflow navigation, not acceptance or implementation status.
Read [ENGINEERING_STATE](../ENGINEERING_STATE.md) for current decisions/seals,
[BUILD_ORDER](../BUILD_ORDER.md) for sequencing, and the assigned packet for the
authorized outcome. Historical packets do not establish current permission.

## ChatGPT Project

1. Keep DuskWeave in its own Project and use
   [PROJECT_INSTRUCTIONS](PROJECT_INSTRUCTIONS.md) as its instruction source.
2. Connect current DuskWeave authority; exclude unrelated project authority.
3. Use duskweave-engineering for architecture and packet preparation,
   build-duskweave for assigned delivery, and duskweave-adversarial-review
   for a distinct review session.
4. Start one conversation per bounded outcome; preserve a compact handoff.

Project instructions guide behavior; they do not guarantee memory isolation or
automatically update application settings. Treat recalled status as unverified.

## IDE

Open D:/DuskWeave or a verified isolated worktree. Follow AGENTS.md.
Load the repository skill matching the task under .agents/skills/.
Preserve the offensive campaign identity and accepted boundaries. Authorized
active validation is not replaced by passive monitoring. A current local-only
milestone does not authorize target acquisition or execution.

## Source ownership

- PRDs/accepted ADRs/contracts: product and architecture authority.
- AGENTS.md: contributor protocol and authority-loading rules.
- QUALITY_BAR.md: gates, evidence requirements and budgets.
- BUILD_ORDER.md: dependency navigation.
- ENGINEERING_STATE.md: acceptance/seal status.
- Skills: role-specific workflows, never runtime campaign agents.
- Packet: exact current task, edit map, tests and completion boundary.

Repository copies govern repository procedure. Use
[skill maintenance](SKILL_MAINTENANCE.md) to publish and verify installed copies.
Keep only short domain anchors in skills; do not copy current stage/HEAD/seals.

## Next permitted work

Resolve current work from engineering state, sequencing and the assigned packet.
Verify actual branch/HEAD and open delivery state before issuing a new packet.
Do not restart a historical design packet because an old prompt names it.
Distinguish unmerged candidate implementation from protected-branch state.

## Completion and handoff

Report verified base/head, packet, changed files, actual checks and environment,
wiring evidence when executable, findings, remaining blockers and next action.
Distinguish authored, reviewed, accepted, merged and sealed.
Do not claim local or remote checks that were not observed.

## Setup verification

Check frontmatter, resource links, size, authority consistency and domain anchors.
For skill changes, exercise realistic tasks before release as described in
skill maintenance. Document-only verification does not establish runtime quality.
